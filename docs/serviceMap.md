## 🔒 Runtime boundaries

`accountsService` owns password credentials; `authService` owns authorization principals and tokens. `virtualMoney` would own one internal ledger and table escrow; `cryptoService` would only adapt agreed external observations. `pokerService` coordinates one authoritative engine instance per table and serializes commands. A player receives only the allowed public/player view, never the trusted server view. No service reads or writes another service's database.

The engine's newline-delimited JSON/TCP server and curses client demonstrate flows without production TLS or authentication. They are references, not a selected production transport. The SDK's HTTP control plane does not imply WebSocket or gameplay transport support. No lobby, gateway, separate funds ledger, blockchain indexer, custody or wallet repository is implied by this map.

## 📦 Verification and open decisions

The auth/accounts file migration and installed-wheel infrastructure startup were checked locally. Disposable PostgreSQL readiness and historical `alembic upgrade head` passed for the generic DB render and both services; those revisions can create the historical tables on an empty database. Docker image build, GitHub CI, next desktop login, and production behavior remain separate checks. Infrastructure readiness is not gameplay, token issuance, ledger or payment readiness.

The `virtualMoney` source needs its exact existing URL with access or a Git bundle. Product decisions still needed: table transport and durable ownership; account/token operations; internal ledger contract; whether deposits or withdrawals exist; external networks/assets/provider, custody/signing, amount units, finality/reversal, retries, reconciliation and permissions. No business endpoint or migration is authorized by this map.
